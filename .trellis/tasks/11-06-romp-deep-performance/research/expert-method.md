# Romp 深入性能方法：从原始证据到可推翻结论

基线：独立检出的 e2a92895857fbfd1fc42e34f1770a32cbffb09cd；本轮无运行测量、无构建/测试、无产品代码变更。三份源码审查的 [H]/[U] 不得当作性能结论。

## 专家先做的额外动作

1. 把目标换成可观察事件：进程启动→窗口→WebView 首帧→输入可用→首条会话内容→切换完成→取消生效→退出且子进程归零。现有 perf.md 的「冷启」只覆盖到窗口句柄，不覆盖可用性。
2. 建立身份链：源码提交、release/debug 构建、二进制哈希、WebView2/Node/sidecar 版本、硬件与电源计划、配置和插件集、输入数据。旧日志、旧文档数字与当前代码不得混用。
3. 画清所有权与关键路径：tab 状态、session 绑定、sidecar、stats、scheduler 子进程、事件订阅，谁创建、谁保留、谁释放。区分阻塞在前台的任务和空闲后台任务。
4. 先问「哪些工作可以少做」，再问「用什么语言做」：重复启动、重复 hydrate、后台 tab 仍向 WebView 发送被丢弃的事件、常驻但未被使用的进程、无必要的二次读取。每个都是假设，需 profile/trace 证实。
5. 先定义否决条件：会话串线、恢复错会话、子进程泄漏、丢失队列/审批、后台运行完成通知丢失或性能收益低于迁移风险，则优化失败。

## 收益上限

若候选只影响用户总等待的比例 p，该段加速 s 倍且其余不变，则总加速比 = 1/((1-p)+p/s)。例：p=10%、s=10 时约 1.10 倍；p=10%、s=∞ 时约 1.11 倍。这是计算示例，不是 Romp 测量。并行优化需按关键路径重新建模。

## 条件化优化顺序（不是实施清单）

阶段 0「先修测量」：保留独立运行日志偏移量，只匹配本次 run；改以 InputArea.tsx:1174-1182 的可用判据配合首帧/首条内容作为终点；进程归属全部从 app pid 树内取，不再按全局 omp.exe 名匹配；区分 WorkingSet、private commit、CPU、句柄；-Tabs 必须真正驱动 tab，记录原始样本而非只留 doc。若这些都做不到，后续任何 A/B 都不可信。

阶段 1「排除重复工作」：验证 tab:get-all、tab:set-active、showView、ready 是否重复触发 hydration；记录每个 activation 的 sidecar 请求数、响应字节、waterfall；确认后台 tab 的事件是否跨 bridge 后被丢弃。只有 trace 证明重复或无效字节占关键等待/CPU 时，才减少请求、合并或过滤。

阶段 2「减少常驻资源」：验证 stats 子进程在典型会话是否必需、启动抢占是否影响首次可用；验证 eviction 的触发频率、resume 成本和空闲 tabs 数量。若 resume 接近 cold spawn，则回收只是冷会话内存杠杆。任何共享/回收进程模型改变前先核对 leases。

阶段 3「Rust 内部与进程边界」：在上述证据表明某条 CPU/序列化/复制路径主导后，再比较减少 clone/复制、改变 batch 边界、收窄 IPC 或替换一个独立 helper。不要先全量重写；Rust 已存在，语言替换本身不是优化。

阶段 4「架构变化」：只有证明主要成本来自进程/WebView 基线且可接受隔离/兼容风险，才评估共享 agent 或替代 UI 路径。

## 独立证明链

- 预注册：目标端点、成功条件、性能门槛、正确性不变量、排除规则、样本与统计量，实验前冻结；不得跑完挑指标。
- 双层 workload：固定 sidecar 响应/合成会话回放隔离本地开销；真实模型/工具任务复测用户可感知结果。固定模型名不代表网络确定性，记录可获得的服务版本和响应元数据。
- 对照：同一机器同一构建、A/B 随机交错、冷/热分开、预热与 GC/文件系统状态记录；多批次报告全样本、p50/p95、置信区间、失败/超时，不报单次最优。
- 正确性：会话绑定唯一且恢复相同；switch_session 仅 success && cancelled===false 更新 ownership；运行中/审批/队列/浏览器/终端/调度任务禁止被回收；事件顺序和后台完成通知不丢失；退出和强杀后进程树归零；布局恢复保持 active tab。
- 负控：故意插入延迟、漏掉一个事件、制造旧会话残留，判定器必须报错；否则测量无效。
- 独立复现：固定提交/二进制哈希、脱敏输入、命令、原始 trace/CSV、分析程序、判定器及失败样本；另一位执行者在另一台机器按包重算。现有单元测试不启动真实 omp.exe，不足以证明端到端行为。
- 可形式化范围：对抽出的小型并发状态机可用 Loom/Kani 检查交错或性质，但必须明示假设；不能据此宣称整个应用被证明。

## 目前最强的条件结论

当前最值得先做的研究不是增加功能或换语言，而是修复测量终点与进程归属、查清 activation 的重复/后台工作、查清常驻进程和回收成本。原因不是「Rust 慢」，而是源码显示已有懒启动、原地切换、页数化 transcript 与 LRU 回收，而旧测量无法验证它们对可用延迟/实际内存的效果。任何加速倍数都须留到实测之后。
